# معمارية النسخ الموثوق — قرار تصميم قبل التنفيذ

**الحالة:** قرار معماري مقترح للمراجعة، لا يحتوي SQL أو كودًا تنفيذيًا، ولا ينشئ موارد أو صلاحيات فعلية.  
**النطاق:** النسخ اليدوي، نسخة الأمان قبل الاستبدال، واستعادة البيانات التشغيلية فقط.  
**الوثائق المرتبطة:** `BACKUP_RESTORE_PROTOCOL.md` و`SQL_EXECUTION_BLUEPRINT.md` و`ENFORCEMENT_MATRIX.md` و`TECHNICAL_DESIGN.md`.

## 1. القرار المعماري

يعتمد التصميم مكوّنًا خادميًا موثوقًا واحدًا لتنسيق عمليات النسخ والاستعادة، مثل Supabase Edge Function، مع حاوية Supabase Storage خاصة للملفات المؤقتة ونسخ الأمان. هذا اختيار تصميمي مشروط بمراجعة حدود الحجم والمهل والصلاحيات في بيئة معزولة قبل اعتماده للتنفيذ.

- المتصفح لا يقرأ جداول البيانات لتكوين النسخة، ولا يبني ZIP من استجابات متعددة، ولا يملك مفتاح `service_role`.
- يتحقق المكوّن الخادمي من رمز جلسة المستخدم ومن مطابقة المستخدم للمالك المهيأ، قبل أي إجراء حساس. لا يقبل هوية المالك من حقل يرسله العميل.
- تحفظ أسرار الخادم في إعدادات أسرار الخدمة فقط، ولا تكتب في المستودع أو السجلات أو ملفات النسخة أو الاستجابات.
- جميع عمليات التخزين الخاصة تتم من المكوّن الموثوق؛ لا وصول عام للحاوية، ولا مسارات كتابة/قراءة عامة للعميل، ولا روابط دائمة مكشوفة.
- يستدعي المكوّن إجراءات PostgreSQL محددة ومحدودة الصلاحيات، ولا ينفذ SQL اعتباطيًا مأخوذًا من المدخلات.
- يجب أن تكون أسماء الملفات ومسارات التخزين وإصدارات الصيغة ثابتة أو مولدة خادميًا؛ لا يسمح للعميل بتحديد مسار تخزين اعتباطي أو استبدال كائن موجود.

**شرط اعتماد:** إذا لم تثبت مراجعة البيئة أن المكوّن قادر على معالجة حجم النسخة ضمن حدود التشغيل والذاكرة والوقت، فلا يُطلق مسار النسخ أو الاستعادة. لا يجوز حل تجاوز الحدود بالتقسيم إلى قراءات غير متسقة أو إسقاط سجلات بصمت.

## 2. نموذج التخزين والوصول

- حاوية خاصة مخصصة للنسخ، منفصلة عن أي ملفات عامة في التطبيق.
- لكل عملية معرّف عشوائي يولده الخادم، ويستخدم مسارًا ثابت البنية؛ لا يعاد استخدام المسار ولا يستبدل كائن سابق.
- تحفظ نسخة الأمان المؤقتة حتى انتهاء العملية والتحقق منها، ثم تطبق سياسة احتفاظ محددة قبل الإطلاق. لا تُحذف نسخة الأمان مباشرة بعد نجاح الاستبدال.
- النسخة ZIP غير مشفرة وفق القرار الوظيفي الحالي؛ لذلك يعد التخزين الخاص وتقييد الوصول والتحذير للمستخدم ضوابط لازمة لكنها لا تعادل التشفير. لا يُسمح بتنزيلها إلا للمالك الموثق عبر استجابة/رابط قصير الصلاحية بعد تحقق الخادم.
- لا تتضمن الحزمة Auth أو كلمات المرور أو الجلسات أو الأسرار أو `system_config.owner_user_id`.
- لا توضع محتويات النسخة أو رموز الجلسات أو الأسرار أو روابط التنزيل السرية في سجلات التطبيق.

## 3. مسار إنشاء نسخة يدوية

1. يتحقق المكوّن الخادمي من جلسة المالك، ويبدأ محاولة مؤقتة بمعرّف عشوائي.
2. تفعّل عملية موثوقة بوابة `maintenance_gate` وتنتظر الكتابات السابقة. تبقى كل الكتابات التشغيلية مرفوضة ما دامت البوابة في `maintenance`.
3. يطلب المكوّن لقطة واحدة متسقة تشمل كل المجموعات المطلوبة والبيانات التاريخية والحجوزات والمولدات اللازمة. لا يقرأ الجداول في أوقات مستقلة، ولا يسمح بكتابة موازية.
4. يثبت المكوّن اللقطة في مخرجات ثابتة داخل المسار الموثوق، ثم ينشئ ZIP و`manifest.json` ببصمات SHA-256 وأحجام الملفات وإصدار التنسيق والمخطط ووقت UTC.
5. يعيد فتح ZIP من التخزين، ويفحص المسارات والملفات المطلوبة والأنواع والأحجام والبصمات، ويتأكد أن كل مجموعة مطلوبة موجودة حتى إن كانت فارغة.
6. **لا تعاد البوابة إلى `normal` إلا بعد نجاح التحقق من الكائن المخزن وثبوت إمكانية قراءته.** عندها فقط يمكن إنشاء رابط تنزيل قصير الصلاحية للمالك.
7. بعد تأكيد التخزين والتحقق، ينتهي وضع الصيانة ويمكن أن يستمر التنزيل من الملف الثابت دون إعادة قراءة قاعدة البيانات.
8. إذا تعذر إثبات اكتمال اللقطة أو التخزين أو التحقق، لا تعلن العملية نجاحًا ولا تنشئ رابط تنزيل. تبقى البوابة في وضع الصيانة إلى أن يُجرى تحقق واستئناف إداري موثوق. لا إعادة تلقائية.

## 4. نسخة الأمان قبل الاستبدال

هذا المسار لا يعيد فتح البوابة بين التقاط نسخة الأمان وتطبيق الاستبدال:

1. تنفذ المعاينة الأولية دون كتابة، وتعرض التعارضات للمستخدم.
2. بعد تأكيد مستقل، يبدأ المكوّن محاولة صيانة واحدة ويقفل الكتابات.
3. يأخذ نسخة أمان من الحالة الحالية تحت البوابة نفسها، وينشئ ZIP في التخزين الخاص، ثم يعيد قراءته ويفحصه بالكامل.
4. تظل البوابة في `maintenance`؛ لا يستدعي هذا المسار إجراء إنهاء النسخ اليدوي الذي يعيد الحالة إلى `normal`.
5. يعيد فحص ملف الاستعادة والتعارضات والحجوزات والمولدات بعد دخول الصيانة؛ لا يعتمد على المعاينة القديمة.
6. يطبق تغييرات PostgreSQL التشغيلية والحجوزات الواردة في معاملة واحدة. لا تتغير Auth أو إعدادات المالك. لا يبدأ الاستبدال إذا فشلت نسخة الأمان أو تحققها.
7. يتحقق من الحالة الفعلية بعد المعاملة. لا يعيد الطلب تلقائيًا عند انقطاع الاتصال أو غموض نتيجة `COMMIT`.
8. لا تُعاد البوابة إلى `normal` إلا بعد تحقق موثوق من النتيجة ومن بقاء نسخة الأمان قابلة للقراءة. عند الغموض تبقى الصيانة مفعلة حتى قرار إداري بعد فحص الحالة.

## 5. الاستعادة من ملف يقدمه المستخدم

- يرفع المستخدم الملف إلى مسار استقبال خاص عبر المكوّن الموثوق؛ لا يُوثق اسم الملف أو نوعه أو `manifest` لمجرد ورودها من العميل.
- يفحص المكوّن الحزمة دون كتابة في قاعدة البيانات: سلامة ZIP، منع مسارات traversal، قائمة الملفات المسموحة، غياب الملفات المطلوبة، أحجام الملفات وعددها، إصدار المخطط، البصمات، الأنواع والعلاقات.
- لا تثبت SHA-256 أصالة الملف أو هوية UUID التاريخية؛ يظل فحص الحجوزات وروابط الهوية إلزاميًا داخل قاعدة البيانات وتحت البوابة.
- يرفض الملف المجهول أو الكبير فوق الحدود المعتمدة أو الناقص أو الملتبس قبل أي تغيير. لا تُحوّل الملفات المفقودة إلى مجموعات فارغة، ولا تُقص البيانات أو تتجاوز القيود.
- بعد التأكيد، تتبع العملية بروتوكول نسخة الأمان والاستبدال في القسم 4.

## 6. فشل التشغيل والاستئناف

- لا توجد مهلة تلقائية تفتح الكتابات، ولا إعادة تلقائية للاستعادة أو الاستبدال.
- تحتوي `maintenance_gate` فقط على حالة التنسيق ومعرّف المحاولة المؤقت ووقت بدء العملية؛ لا تتحول إلى سجل أحداث دائم.
- إجراء الاستئناف إداري موثوق، منفصل عن واجهة المستخدم العادية، يجب أن يتحقق من معرّف المحاولة والحالة الفعلية للبيانات ووجود نسخة أمان صالحة وعدم وجود تنفيذ ما زال جاريًا قبل إعادة `normal`.
- إذا تعذر إثبات الحالة، تبقى البوابة في `maintenance`. لا يُسمح بإنشاء محاولة جديدة فوق محاولة غير محسومة.
- لا يحق للمستخدم العادي تعديل البوابة أو تجاوزها. يجب أن تُختبر صلاحيات RPC والجداول والحاوية الخاصة، بما في ذلك أن امتيازات الخادم الواسعة لا تتسرب إلى العميل.

## 7. حدود الحجم والتشغيل — شرط قبل الإطلاق

قبل كتابة التنفيذ، يجب تحديد واختبار حد أقصى واضح لحجم ZIP، والحجم بعد الاستخراج، وعدد الملفات، وعدد السجلات، ووقت المعالجة. يجب أن تتوافق الحدود مع إمكانات Edge Function والتخزين وقاعدة البيانات في البيئة الفعلية.

- الحد غير المحدد يعني أن الميزة غير جاهزة للإطلاق.
- تجاوز أي حد يوقف العملية قبل الاستبدال، ولا ينتج نسخة جزئية معلنة على أنها ناجحة.
- يجب اختبار مجموعة بيانات اصطناعية عند الحد وعند تجاوزه، وقطع الاتصال في كل مرحلة، وفشل التخزين، وفشل القراءة الراجعة، ونتيجة `COMMIT` الملتبسة.
- إذا لم تناسب حدود Edge Function حجم البيانات المتوقع، يجب تصميم مكوّن خادمي موثوق بديل قبل التنفيذ؛ لا يتم الارتجال أثناء الاستعادة.

## 8. اختبارات القبول الإلزامية

| المعرّف | الحالة | معيار النجاح |
|---|---|---|
| BAK-TRUST-01 | مستخدم غير المالك يطلب نسخة | رفض دون كشف بيانات أو رابط تخزين |
| BAK-TRUST-02 | كتابة متزامنة قبل تفعيل الصيانة | تنتظر العملية حتى انتهاء الكاتب وتلتقط حالة مكتملة |
| BAK-TRUST-03 | كتابة بعد تفعيل الصيانة | رفض قبل أي تغيير |
| BAK-TRUST-04 | ملف ZIP مخزن يعاد تنزيله وفحصه | جميع الملفات والأحجام والبصمات متطابقة |
| BAK-TRUST-05 | فشل رفع/تخزين/قراءة راجعة | لا نجاح ولا رابط تنزيل؛ الصيانة تبقى حتى التحقق الإداري |
| BAK-TRUST-06 | تجاوز حد الحجم أو الزمن | رفض آمن بلا اقتطاع أو استبدال جزئي |
| RST-TRUST-01 | فشل إنشاء نسخة الأمان | لا يبدأ الاستبدال |
| RST-TRUST-02 | نسخة الأمان صالحة ثم ملف استعادة متعارض | لا تغيير في البيانات؛ نسخة الأمان تبقى متاحة |
| RST-TRUST-03 | انقطاع قبل/بعد COMMIT | لا إعادة تلقائية؛ فحص الحالة الفعلية مع إبقاء الصيانة عند الغموض |
| RST-TRUST-04 | محاولة وصول مباشر من العميل إلى الحاوية أو بوابة الصيانة | رفض وفق السياسات والامتيازات |
| RST-TRUST-05 | تعطل المكوّن بعد تفعيل الصيانة | لا فتح تلقائي؛ الاستئناف الإداري وحده بعد التحقق |

## 9. ما لم يُحسم أو يُنفذ

1. اختيار Supabase Edge Function والحاوية الخاصة هو القرار المعماري المفضل، لكنه مشروط بإثبات حدود الحجم والوقت والذاكرة والامتيازات في بيئة معزولة.
2. يجب تحديد سياسة احتفاظ فعلية لنسخ الأمان ومساحة التخزين وآلية حذف آمنة للملفات المؤقتة بعد انتهاء الاحتفاظ.
3. يجب تصميم إجراءات PostgreSQL الداخلية الدقيقة وتقييد `EXECUTE` والامتيازات، والتحقق من أن المكوّن الخادمي وحده يستطيع تشغيل عمليات الصيانة.
4. يجب تحديد حدود الحجم الرقمية قبل الإطلاق، بناءً على اختبار فعلي لا على التخمين.
5. لم تُكتب SQL أو migrations أو كود، ولم يُنشأ حساب/مشروع Supabase أو حاوية تخزين، ولم تُشغّل اختبارات. هذه مواصفة تصميم فقط.
