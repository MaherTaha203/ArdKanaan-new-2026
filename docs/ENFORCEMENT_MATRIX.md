## بوابات ما قبل SQL

1. جرد الجداول والقيود والفهارس والمشغلات والدوال والملكية والامتيازات وسياسات RLS.
2. جرد الأدوار الفعلية وتمييز anon وauthenticated ومالك Auth ومالك كائنات PostgreSQL.
3. ربط كل قاعدة بمعرّف اختبار فعلي؛ اسم الاختبار وحده ليس دليل نجاح.
4. اختبار تجاوز الواجهة بأدوار غير مميزة، دون استخدام superuser لإثبات فعالية سياسات الوصول.
5. اختبارات تزامن بجلسات مستقلة للترقيم والتسجيل والدمج والاستعادة.
6. حقن فشل في المراحل الحرجة وإثبات عدم بقاء كتابة جزئية.
7. عند غياب دليل كافٍ على UUID التاريخي، ترفض الاستعادة بدل التخمين.
8. إثبات تعطيل التسجيل العام وتهيئة المالك إداريًا والرفض الافتراضي عند غياب owner_user_id.

**الحدود:** هذه مصفوفة تصميمية لا نتيجة فحص قاعدة حية. لم تُنفذ SQL أو migrations، ولم يُنشأ حساب/مشروع Supabase، ولم تُشغّل اختبارات DB فعلية. لا يوصف النظام بأنه آمن أو جاهز قبل تنفيذ الاختبارات وتوثيق نتائجها.

## مراجعة تنفيذية إضافية — سباقات التزامن وهوية الحجز

هذه التفاصيل إلزامية لتجنب أن تبدو القاعدة صحيحة في الاختبارات المتسلسلة ثم تُخرق تحت طلبات متزامنة:

1. **تسجيل الطالب:** داخل معاملة إنشاء التسجيل، يجب قفل صف الطالب وصف الدورة المناسبين (بترتيب قفل ثابت) أو استخدام آلية مكافئة مثبتة؛ ثم إعادة فحص أن الطالب غير محذوف ونشط وأن الدورة مفتوحة قبل INSERT. يجب أن تتبع عمليات إيقاف الطالب وإغلاق الدورة سياسة القفل نفسها، أو تُثبت اختبارات التزامن أن أي سباق لا ينتج تسجيلًا نشطًا مخالفًا. الفهرس الفريد الجزئي يمنع التكرار فقط ولا يثبت صحة حالة الطالب أو الدورة.
2. **فتح الدورة:** تغيير حالة دورة إلى open يجب أن يتحقق داخل معاملة من عدم وجود دورة أخرى مفتوحة بالاسم المطبع نفسه، مع قيد تفرد جزئي نهائي يمنع السباق بين عمليتي فتح. الفحص في التطبيق أو SELECT وحده لا يكفي.
3. **الدمج:** قفل سجلي الطالبين وكل سجلات التسجيل ذات الصلة بترتيب ثابت، ثم إعادة فحص حالة الدمج والتعارضات النشطة والروابط قبل أي UPDATE. لا تكفي المعاينة السابقة؛ قد تتغير البيانات بعدها.
4. **الاستعادة والاستبدال:** يجب أن يتشارك كل مسار كتابة تشغيلي وكل مسار استعادة/استبدال بروتوكول قفل واحدًا معروفًا، أو يستخدم بروتوكولًا مكافئًا مثبتًا؛ وإلا قد تُضاف حجوزات أو تسجيلات أثناء تكوين لقطة الاستعادة. توثّق حدود المعاملة، وترتيب الأقفال، وكيفية منع التعارض مع الكتابات المتزامنة.
5. **إعادة استخدام حجز الهوية نفسها عند الاستعادة:** إذا كان الحجز موجودًا بالفعل، فلا تُنشأ نسخة ثانية منه. يجوز الاستفادة من الحجز القائم فقط بعد مطابقة نوع المعرف والقيمة المعيارية والهوية التاريخية وروابطها؛ الحجز المطابق لنفس الهوية يُحتفظ به كما هو، أما أي اختلاف أو غموض فيوقف الاستعادة. لا تستخدم UPSERT يغيّر مراجع الحجز التاريخي لإجبار النجاح.
6. **إثبات الذرية:** لا تكتفِ باختبار فشل INSERT واحد. اختبر حقن الفشل بعد كل مرحلة من إنشاء السجل وحجز المعرّف، وبعد كل مرحلة دمج، وخلال الاستعادة بعد تجهيز البيانات وقبل التحقق النهائي؛ يجب ألا يبقى أي أثر جزئي.
7. **اختبار الوصول:** افصل اختبارات API التي تستخدم `anon` و`authenticated` عن اختبارات مالك قاعدة البيانات. لا تثبت جلسة superuser أن RLS تعمل؛ كما لا يكفي فشل طلب من الواجهة لإثبات أن الامتيازات المباشرة مضبوطة.

**معيار القبول الإضافي:** لا تُعتمد آلية الإنفاذ قبل كتابة خطة قفل دقيقة لكل إجراء حساس، ثم تشغيل اختبارات تزامن متعددة الجلسات وحقن الفشل على PostgreSQL/Supabase معزول. ما سبق توصية تنفيذية موثقة، وليس نتيجة اختبار منفذ.


## قاعدة إنفاذ عامة إلزامية — بوابة الصيانة

تُطبق هذه القاعدة على **كل** بند في المصفوفة يكتب أو يغيّر بيانات، حتى لو لم يتكرر ذكرها في عمود موضع الإنفاذ:

1. كل إجراء كتابة موثوق يقفل صف `maintenance_gate` باستخدام `SELECT ... FOR UPDATE` داخل معاملة PostgreSQL، ثم يتحقق أن الحالة `normal` قبل أي كتابة، ويحتفظ بالقفل حتى نهاية المعاملة.
2. يشمل ذلك إنشاء/تعديل/إيقاف الطلاب، إنشاء/فتح/إغلاق الدورات، التسجيلات، الحجوزات والمولدات، تصحيح المعرفات، الدمج، والاستعادة والاستبدال. أي مسار كتابة غير موثق أو مباشر يعد تجاوزًا ممنوعًا.
3. إجراءات تفعيل الصيانة/إعادتها إلى `normal` محصورة في مكوّن إداري موثوق؛ لا يستطيع العميل تعديل البوابة مباشرة. لا تعاد الحالة تلقائيًا عند انتهاء المهلة أو انقطاع الاتصال.
4. لا يُعتمد على advisory lock بديلًا عن قفل صف البوابة، ولا يُفترض اشتراك طلبات HTTP المنفصلة في جلسة PostgreSQL واحدة.
5. **اختبارات القبول:** أثبت أن كاتبًا بدأ أولًا يُكمل قبل تفعيل الصيانة، وأن الكتابات الجديدة تُرفض بعد تفعيلها، وأن كل إجراء كتابة يرفض إذا كانت البوابة في `maintenance`، وأن العميل لا يستطيع تعديل البوابة أو منح نفسه صلاحية تجاوزها.

هذه قاعدة تصميمية لم تُنفذ أو تُختبر بعد. يجب عند كتابة SQL ربط كل إجراء كتابة محدد بهذه القاعدة ضمن جرد الإجراءات والامتيازات، لا الاكتفاء بإضافة البوابة إلى وثيقة التصميم.

## ملحق — سجل تدقيق صلاحيات قاعدة البيانات قبل التنفيذ

قبل إنشاء SQL، أنشئ قائمة فعلية بكل جدول ودالة وإجراء، تتضمن المستدعين المسموحين، ومالك الكائن، وصلاحيات القراءة والكتابة والاستدعاء، وفحوص المالك، وترتيب القفل، والاختبار السلبي المباشر. يجب التحقق من الامتيازات الفعلية في PostgreSQL، وليس الاكتفاء بمراجعة الواجهة أو ملفات التصميم.

القاعدة الافتراضية أن الدوال تعمل بصلاحيات المستدعي. إذا احتاجت دالة إلى صلاحيات مالكها، فيلزم توثيق السبب، وضبط مسار البحث بصورة آمنة، وتأهيل أسماء الكائنات، وسحب صلاحية الاستدعاء العامة، ومنحها فقط للمستدعين المقصودين. لا يجوز أن يستطيع العميل تعديل بوابة الصيانة أو إعداد المالك أو حجوزات المعرفات مباشرة.

لا يُعد هذا الملحق إثباتًا للتنفيذ؛ يجب أن تشمل الاختبارات دورًا مجهولًا، وجلسة المالك، وجلسة غير المالك، وغياب إعداد المالك، ومحاولات الوصول المباشر واستدعاء إجراء غير مخول.
