# مقترح مخطط قاعدة البيانات التفصيلي — ArdKanaan-new-2026

**الحالة:** وثيقة تصميم للمراجعة فقط؛ ليست SQL ولا migration ولا إذنًا بالتنفيذ أو إنشاء موارد.

## 1. قواعد التصميم الحاكمة

- النطاق محصور بالطلاب والدورات والتسجيلات والبحث ولوحة المعلومات والنسخ والاستعادة؛ لا مالية ولا ترحيل من النظام القديم ولا اتصال به.
- حساب بشري واحد فقط، دون أدوار أو دعوات أو تسجيل عام أو إدارة مستخدمين.
- UUID مفتاح داخلي ثابت، منفصل عن الرقم المقروء.
- القيود الحرجة تُفرض في PostgreSQL داخل معاملة، لا في الواجهة وحدها.
- لا يعاد استخدام أي رقم أو رمز سبق حجزه، حتى بعد الحذف المنطقي أو الاستبدال الكامل.
- الحذف المنطقي للطالب لا يحذف تسجيلاته؛ حالة النشاط مستقلة عن الحذف.
- يُحتفظ بميزة دمج الطلاب كعملية استثنائية مستقلة. تتطلب معاينة واضحة للتغييرات والتعارضات، وحسم التعارضات الإلزامية وتأكيدًا صريحًا قبل التنفيذ. تنفذ العملية «كلها أو لا شيء»، وتُعرض نتيجتها الحالية دون حفظ تقارير دائمة.
- كل الأرقام المدخلة والمعروضة تستخدم الأرقام الإنجليزية 0123456789.

## 2. الجداول والعلاقات

العلاقة الأساسية: الطلاب 1 ← N التسجيلات N → 1 الدورات. سجل الحجوزات يحتفظ بتاريخ مستقل عن البيانات التشغيلية؛ لا يُنشأ سجل دائم للعمليات الحساسة.

### 2.1 جدول students — الطلاب

| الحقل | النوع المقترح | Null؟ | الغرض والقيود |
|---|---|---:|---|
| id | uuid | لا | مفتاح أساسي ثابت يولد في قاعدة البيانات. |
| merged_into_student_id | uuid | نعم | مرجع إلى الطالب الأساسي إذا كان هذا السجل مصدرًا لعملية دمج؛ لا يشير إلى الذات أو إلى سجل مدموج آخر. |
| merged_at | timestamptz | نعم | وقت الدمج؛ يجب أن يتوافق مع merged_into_student_id. |
| student_number | text | لا | رقم مثل ST-000001؛ فريد وثابت ومحجوز تاريخيًا. |
| manual_number | text | نعم | رقم اختياري؛ فريد حاليًا وتاريخيًا بعد التطبيع. |
| full_name | text | لا | الاسم بعد إزالة المسافات الطرفية ودمج المسافات المتكررة فقط. |
| phone | text | نعم | هاتف اختياري كنص للحفاظ على الصفر الأول و+؛ ليس مفتاحًا. |
| status | قيمة محددة | لا | active أو suspended فقط. |
| notes | text | نعم | ملاحظات اختيارية؛ الحد الأقصى 1000 حرف، وتُرفض القيم الأطول ولا تُقص. |
| deleted_at | timestamptz | نعم | NULL يعني غير محذوف منطقيًا. |
| created_at | timestamptz | لا | وقت إنشاء من قاعدة البيانات. |
| updated_at | timestamptz | لا | وقت آخر تعديل من قاعدة البيانات. |

القيود والفهارس المقترحة:
- تفرد id وstudent_number، ومنع الاسم الفارغ بعد التطبيع.
- manual_number إن وجد لا يكون فارغًا بعد التطبيع، ولا يتعارض مع سجل حجز.
- تطبيع الرقم اليدوي مبدئيًا: إزالة المسافات من البداية والنهاية فقط، ومقارنة الأحرف الإنجليزية دون حساسية لحالة الحرف، وتجاهل الأصفار الأولى فقط إذا كانت القيمة كلها أرقامًا. تُحفظ الأصفار داخل القيم المختلطة بالحروف أو الرموز. أمثلة: `a-125` و`A-125` متطابقتان؛ `00125` و`125` متطابقتان؛ `AB 125` و`AB125` مختلفتان؛ `  A-125  ` و`A-125` متطابقتان. يلزم تنفيذ التطبيع نفسه بصورة موحدة في التحقق والحجز والبحث والاستعادة.
- فهارس للرقم التلقائي والرقم اليدوي المطبع والاسم والهاتف وفق سلوك البحث الذي سيعتمد.
- القوائم العادية تستبعد deleted_at غير الفارغ؛ لا حذف فعلي من واجهة الاستخدام.
- استعادة الطالب تعيد السجل نفسه ولا تعيد تنشيطه ولا تنشئ تسجيلات جديدة.

### 2.2 جدول courses — الدورات

| الحقل | النوع المقترح | Null؟ | الغرض والقيود |
|---|---|---:|---|
| id | uuid | لا | مفتاح أساسي ثابت. |
| course_code | text | لا | رمز مثل CR-0001؛ فريد وثابت ومحجوز تاريخيًا. |
| name | text | لا | اسم بعد تطبيع المسافات الطرفية والمتكررة فقط. |
| start_date | date | نعم | تاريخ بداية اختياري. |
| end_date | date | نعم | تاريخ نهاية اختياري. |
| status | قيمة محددة | لا | open أو closed؛ لا يغلق التاريخ الدورة تلقائيًا. |
| notes | text | نعم | ملاحظات اختيارية. |
| created_at | timestamptz | لا | وقت الإنشاء. |
| updated_at | timestamptz | لا | وقت آخر تعديل. |

القيود والفهارس المقترحة:
- تفرد course_code.
- end_date لا يسبق start_date إذا كانا موجودين معًا.
- منع الاسم المطبع المكرر بين الدورات المفتوحة فقط. لا تطبيع للحروف أو الهمزات أو علامات الترقيم.
- فهرس بحث بالاسم والحالة وتاريخ النهاية عند الحاجة.
- انتهاء التاريخ لا يغير status تلقائيًا.

### 2.3 جدول enrollments — التسجيلات

| الحقل | النوع المقترح | Null؟ | الغرض والقيود |
|---|---|---:|---|
| id | uuid | لا | مفتاح أساسي لكل واقعة تسجيل. |
| student_id | uuid | لا | الطالب الأساسي الحالي الذي يُنسب إليه التسجيل بعد الدمج؛ مفتاح أجنبي إلى students.id. |
| original_student_id | uuid | لا | الطالب الذي أُنشئ التسجيل له أول مرة؛ ثابت ولا يتغير عند الدمج، ومفتاح أجنبي إلى students.id. |
| course_id | uuid | لا | مفتاح أجنبي إلى courses.id. |
| status | قيمة محددة | لا | active أو completed أو withdrawn أو cancelled. |
| enrolled_at | timestamptz | لا | وقت التسجيل الفعلي، افتراضيًا من قاعدة البيانات. |
| notes | text | نعم | ملاحظات اختيارية. |
| created_at | timestamptz | لا | وقت إنشاء السجل. |
| updated_at | timestamptz | لا | وقت آخر تعديل. |

القيود والفهارس المقترحة:
- مفاتيح أجنبية إلى الطالب والدورة، ودون حذف تتابعي للسجلات المرتبطة. يجب أن يبقى original_student_id ثابتًا حتى بعد تغيير student_id في الدمج.
- فهرس فريد جزئي يمنع تسجيلين active للزوج نفسه من الطالب والدورة.
- فهارس لعرض تسجيلات الطالب أو الدورة حسب الحالة والتاريخ.
- إنشاء تسجيل active يتطلب طالبًا غير محذوف ونشطًا ودورة مفتوحة. يجب أن يكون الفحص والإنشاء ذريين داخل قاعدة البيانات.
- لا يعاد تسجيل نهائي إلى active؛ ينشأ تسجيل جديد. يجب فرض انتقالات الحالة في قاعدة البيانات أو مسار كتابة محمي لا يمكن تجاوزه عبر API.
- إيقاف الطالب أو إغلاق الدورة لا يغير التسجيلات القائمة تلقائيًا.

### 2.4 جدول identifier_reservations — سجل حجز المعرفات الدائم

| الحقل | النوع المقترح | Null؟ | الغرض والقيود |
|---|---|---:|---|
| id | uuid | لا | مفتاح أساسي لسجل الحجز. |
| identifier_kind | قيمة محددة | لا | student_number أو student_manual_number أو course_code أو student_uuid أو course_uuid؛ حجز UUIDs تاريخيًا إلزامي. |
| normalized_value | text | لا | القيمة المعيارية المستخدمة في التفرد. |
| display_value | text | لا | القيمة كما خُصصت أول مرة. |
| student_id | uuid | نعم | مرجع تاريخي اختياري إلى الطالب الحالي. |
| course_id | uuid | نعم | مرجع تاريخي اختياري إلى الدورة الحالية. |
| reserved_at | timestamptz | لا | وقت الحجز الأصلي. |
| reservation_reason | text | لا | مثل created أو manual_assignment أو correction_old_value أو restore_import. |

القواعد الإلزامية:
- تفرد الزوج (identifier_kind, normalized_value).
- بالنسبة إلى `student_manual_number`، تُحسب `normalized_value` وفق قرار التطبيع المبدئي: إزالة المسافات الطرفية، ومقارنة الأحرف الإنجليزية دون حساسية لحالة الحرف، وتجاهل الأصفار الأولى إذا كانت القيمة أرقامًا فقط.
- لا تمحى الحجوزات عند الحذف أو التصحيح أو الدمج أو الاستبدال الكامل.
- **قرار معتمد مبدئيًا — حجز UUIDs التاريخية:** يحجز UUID كل طالب وكل دورة عند تخصيصه، ويظل محجوزًا حتى لو اختفى السجل التشغيلي بعد الاستبدال الكامل. لا يجوز تخصيص UUID محجوز لسجل جديد.
- إذا أعادت نسخة احتياطية سجل طالب أو دورة باستخدام UUID موجود في سجل الحجز، فيجب التحقق مما إذا كان هوية السجل التاريخي نفسه أم تعارضًا؛ لا يُنشأ سجل جديد ولا يُغيّر ارتباط UUID بصمت. أي تعارض هوية غير محسوم يوقف الاستعادة قبل الكتابة.
- لا تعتمد حجوزات UUID على FK قابلة للكسر عند حذف السجلات التشغيلية؛ يجب أن يحتفظ سجل الحجز بالقيمة التاريخية ونوع الكيان حتى إن لم يعد السجل الأصلي موجودًا.
- التوليد والحجز وإنشاء السجل المرتبط تتم في معاملة واحدة.
- تصحيح الرقم اليدوي يحجز الرقم الجديد ويبقي القديم محجوزًا ويسجل السبب؛ لا يُحرر القديم لإعادة الاستخدام.
- الاستعادة تضيف الحجوزات الواردة إلى الحالية؛ التصادم يوقف التنفيذ أو يظهر كتعارض صريح.
- لا تستخدم ON DELETE CASCADE للحجوزات. يلزم حسم هل تحفظ المراجع بلا FK أم تفصل المراجع التاريخية عن الروابط الحية، لأن الحجز يجب أن يبقى بعد الاستبدال.

### 2.5 جدول system_config — إعداد الحساب الوحيد

هذا الجدول الإضافي المقترح يسد فجوة في التصميم: تحتاج RLS إلى مرجع ثابت للحساب المسموح. لا ينشئ أدوارًا أو حسابات متعددة.

| الحقل | النوع المقترح | Null؟ | الغرض والقيود |
|---|---|---:|---|
| singleton_key | boolean | لا | المفتاح الأساسي، وقيمته الوحيدة true. |
| owner_user_id | uuid | لا | معرّف حساب Supabase Auth المصرح به. |
| created_at | timestamptz | لا | وقت التهيئة. |
| updated_at | timestamptz | لا | وقت آخر تعديل إداري موثوق. |

- صف واحد فقط؛ لا يستطيع العميل العادي إدخاله أو تعديله أو حذفه.
- يهيأ owner_user_id من مسار إداري موثوق؛ لا يُقبل أن يصبح أول مستخدم مسجل هو المالك تلقائيًا.
- تعطيل التسجيل العام ومنع إنشاء حساب ثانٍ واستعادة الوصول تحتاج تصميمًا واختبارًا منفصلين.
- تقارن RLS هوية auth.uid() بالمالك عبر سياسة/دالة محمية. إذا استخدمت دوال SECURITY DEFINER فيجب تدقيق search_path والصلاحيات.
- RLS وحدها لا تكفي للعمليات الحساسة؛ يجب أن تعيد إجراءاتها التحقق من الجلسة والمالك والقيود.

## 3. توليد المعرفات وعدم إعادة استخدامها

- رقم الطالب: ST- متبوعًا بتسلسل أرقام إنجليزية، عرض أدنى 6 خانات؛ رمز الدورة: CR- بعرض أدنى 4 خانات. الطول حد أدنى لا سقف.
- تُخزن المعرفات المقروءة كنص للحفاظ على البادئة والأصفار.
- التوليد من مولد ذري في PostgreSQL، لا من MAX+1 ولا من الواجهة. قد تُستهلك قيمة عند فشل معاملة؛ هذا مقبول وأفضل من إعادة استخدامها.
- المولد وحده لا يمنع التصادم مع قيمة مستوردة أو محجوزة؛ يلزم فحص سجل الحجز وقيد التفرد داخل المعاملة.
- **قرار معتمد مبدئيًا — الاستعادة لا تُرجع الترقيم إلى الخلف:** لا يجوز خفض مولد رقم الطالب أو رمز الدورة إلى قيمة النسخة الاحتياطية إذا كان النظام قد خصص قيمًا أعلى من ذلك سابقًا. مثال: إذا وصل النظام إلى `ST-000250` وكانت النسخة تنتهي عند `ST-000180`، فلا يجوز البدء مجددًا من `ST-000181`.
- قبل الاستعادة، تُقارن الحجوزات الحالية والواردة، ويُحتفظ بكل الحجوزات الحالية ويُضاف إليها الوارد غير المتعارض. لا يعاد استخدام أي رقم محجوز، حتى إن غاب عن النسخة القديمة أو عن البيانات التشغيلية الحالية.
- بعد الاستيراد، يضبط كل مولد إلى قيمة آمنة لا تقل عن موضعه الحالي ولا عن أعلى رقم متوافق تم استيراده أو حجزه، وفق آلية متزامنة آمنة. لا يجوز أن يؤدي ضبط المولد إلى الخلف إلى إعادة استخدام رقم. تفاصيل الآلية بوابة قبل SQL.
- إذا تعارضت قيمة مستوردة مع حجز تاريخي قائم أو تعذر إثبات موضع ترقيم آمن، تتوقف الاستعادة قبل الكتابة إلى أن يُحل التعارض صراحة؛ لا إعادة ترقيم صامتة ولا تخطٍّ صامت للسجلات.
- إدخال الرقم اليدوي أو استيراد معرف يمر عبر إجراء يحجز القيمة ضمن المعاملة. يحجز UUID الطالب أو الدورة أيضًا عند الإنشاء والاستيراد، ولا يحل UUID محل الرقم المقروء.
- عند استعادة نسخة، تُفحص UUIDs الطلاب والدورات الواردة مقابل سجل الحجوزات التاريخي. يُسمح باستعادة هوية السجل الأصلي فقط إذا أمكن إثبات المطابقة وفق قواعد الاستعادة؛ وإلا يتوقف التنفيذ لتسوية التعارض.

## 4. مصفوفة الإنفاذ والاختبار

| القاعدة | الإنفاذ المطلوب | اختبار القبول |
|---|---|---|
| الرقم التلقائي ورمز الدورة فريدان | قيد DB وسجل الحجز | طلبان متزامنان لا يحصلان على القيمة نفسها. |
| الرقم اليدوي لا يعاد استخدامه | إجراء موثوق وسجل حجز وقيد فريد حالي | لا يعاد استخدامه بعد الحذف أو التصحيح أو الاستعادة. |
| اسم الدورة فريد بين المفتوحة | قيد/فهرس متوافق مع التطبيع | رفض الاسم المطبع المكرر للدورات المفتوحة. |
| نهاية الدورة لا تسبق البداية | قيد DB | رفض الترتيب الخاطئ والسماح بتاريخ منفرد. |
| لا تسجيل نشط مكرر | فهرس فريد جزئي أو مكافئ DB | طلبان متزامنان؛ واحد فقط ينجح. |
| الطالب/الدورة صالحان للتسجيل النشط | إجراء ذري في DB | رفض طالب موقوف أو محذوف ودورة مغلقة. |
| لا إعادة تنشيط نهائي | مسار كتابة محمي/قيد انتقال | رفض تحويل completed/withdrawn/cancelled إلى active. |
| الحجوزات تبقى بعد الاستبدال | تصميم معاملة الاستعادة | نسخة قديمة لا تمحو الحجوزات الحالية. |
| الوصول للحساب الوحيد | Auth وRLS وإجراءات محمية | الجلسة غير المصرح بها لا تقرأ ولا تكتب. |

## 5. RLS والصلاحيات

- تفعيل RLS على كل جدول مكشوف للعميل.
- لا صلاحية عامة لـ anon، ولا تسجيل عام ولا قراءة عامة.
- القراءة والكتابة التشغيلية للحساب الذي يطابق auth.uid() قيمة owner_user_id.
- لا صلاحية مباشرة للعميل لتعديل identifier_reservations أو system_config؛ تكتب عبر إجراءات محدودة موثوقة.
- تدقيق صلاحيات authenticated وanon ومالك الجداول والدوال. لا يوضع مفتاح service_role في الواجهة أو المستودع أو النسخ.
- لا يستطيع المستخدم تعيين نفسه مالكًا أو تعديل owner_user_id أو إضافة حساب آخر.
- تعاد مراجعة المصادقة والمالك عند تنفيذ العمليات الحساسة، وليس في المعاينة فقط.

## 6. النسخ الاحتياطي والاستعادة

### 6.1 ملفات ZIP المقترحة

- manifest.json: التطبيق، إصدار تنسيق النسخة، وقت التصدير UTC، إصدار المخطط، قائمة الملفات وأحجامها وبصماتها.
- students.json
- courses.json
- enrollments.json
- identifier_reservations.json

لا تشمل الحزمة `system_config` أو بيانات Supabase Auth أو كلمات المرور أو رموز الجلسات أو الأسرار. **قرار معتمد — لا يوجد سجل دائم للعمليات الحساسة:** لا يُنشأ جدول `operation_events` ولا سجل تدقيق دائم لعمليات الدمج أو الاستعادة أو الاستبدال. لا تعتمد سلامة التنفيذ على سجل أحداث؛ بل على المعاينة والتأكيد، والمعاملة الذرية، والتحقق من النتيجة قبل إعادة المحاولة. يمكن عرض نتيجة العملية الحالية للمستخدم دون حفظ سجل دائم.

### 6.2 الفحص والمعاينة قبل الكتابة

### 6.3 دمج الطلاب والاستبدال الكامل

- دمج الطلاب ميزة معتمدة، لكنها استثنائية وليست تلقائية. يختار المستخدم صراحةً الطالب الأساسي الذي سيبقى والطالب الآخر الذي ستُدمج بياناته فيه. يعرض النظام السجلين والفروق والتسجيلات المتأثرة والتعارضات قبل التأكيد.

- **قرار معتمد — أرقام الطلاب بعد الدمج:** يبقى الرقم التلقائي للطالب الذي اختفى سجله التشغيلي بسبب الدمج محجوزًا بصورة دائمة في سجل الحجوزات التاريخي، ولا يُمنح لأي طالب جديد. لا يغير الدمج رقم الطالب الأساسي ولا يعيد ترقيم التسجيلات التاريخية.
- **قرار معتمد — الرقم اليدوي بعد الدمج:** يبقى الرقم اليدوي للطالب المدموج محجوزًا تاريخيًا بعد اختفاء سجله التشغيلي، وفق قواعد التطبيع المعتمدة، ولا يجوز تخصيصه لطالب آخر. يبقى الرقم اليدوي للطالب الأساسي كما هو؛ وأي تعارض يُحسم صراحةً قبل التنفيذ. يجب حل التعارضات قبل الكتابة؛ وتنفذ كل تغييرات الدمج في معاملة ذرية واحدة، وإلا تتراجع كلها. لا يُنشأ سجل دائم لعملية الدمج، وتظهر النتيجة للمستخدم فقط.

- الدمج لا يحذف سجلًا حاليًا لمجرد غيابه عن النسخة، ولا يغيّر بصمت الحقول المحمية أو حالة التسجيل أو روابطه.
- لا يُحذف سجل الطالب المصدر عند الدمج؛ يُعلّم بأنه مدموج في الطالب الأساسي ويُخفى من القوائم التشغيلية العادية. تُحفظ بيانات هويته وملاحظاته ومعرّفاته التاريخية.
- الاستبدال الكامل يغير students وcourses وenrollments فقط. الحجوزات الحالية لا تستبدل بل تضاف إليها حجوزات واردة صالحة؛ system_config والمصادقة والمخطط لا تُمس.
- قبل الاستبدال، تنشأ نسخة أمان حديثة ويُتحقق من قابليتها للقراءة. فشل النسخة أو التحقق يمنع الاستبدال.
- تأكيد مستقل للاستبدال، لا يتحول إلى دمج تلقائيًا أو العكس.
- التغييرات التشغيلية في معاملة ذرية؛ أي فشل يتسبب في تراجع كامل.
- حُسم: لا يُنشأ سجل دائم للعمليات الحساسة. وتُحجز UUIDs الطلاب والدورات تاريخيًا ولا تُعاد استخدامها بعد اختفاء السجل التشغيلي. تبقى كيفية تمثيل روابط السجل التاريخي دون FK مدمرة وتفريق الهوية الأصلية عن التصادم غير المحسوم تفصيلًا تقنيًا يجب إثباته قبل SQL.
- بعد التنفيذ، يعاد التحقق من الأعداد والعلاقات والحالات والحجوزات.

### 6.4 التزامن ومنع التكرار

- تعاد جميع الفحوص داخل التنفيذ لأن البيانات قد تتغير بعد المعاينة.

## 9. قرارات يجب إثباتها تقنيًا قبل SQL أو migrations

1. **محسوم:** الحدود القصوى: اسم الطالب 100، اسم الدورة 100، الهاتف 20، الرقم اليدوي 30، الملاحظات 1000 حرف؛ تُرفض القيم الأطول ولا تُقص.

3. **حُسم مبدئيًا:** الاستعادة لا تخفض مولدات أرقام الطلاب أو رموز الدورات؛ تبقى الحجوزات الحالية وتُضاف إليها الواردة، ويوقف أي تعارض قبل الكتابة. ما زالت تفاصيل آلية الضبط المتزامن للمولدات بوابة تقنية قبل SQL؛ لا MAX+1.
4. **حُسم مبدئيًا:** حجز UUIDs الطلاب والدورات تاريخيًا بعد الاستبدال الكامل، وعدم إعادة استخدامها. تبقى آلية تمثيل المراجع التاريخية والتحقق من استعادة الهوية الأصلية بوابة تقنية قبل SQL.

9. اعتماد أسماء ملفات النسخة وإصدارها وصيغ التاريخ والبصمات وحدود ZIP. البصمة وحدها ليست إثباتًا لمصدر موثوق أو حماية من العبث.
10. آلية أخذ لقطة متسقة أثناء التصدير والتعامل مع الكتابات أثناء النسخ.
11. آلية قفل الاستعادة ومهلة القفل وترتيب المعاملات والتحقق من الحالة الفعلية عند انقطاع الاتصال، دون سجل نتيجة دائم.
12. إعداد Supabase Auth للحساب الوحيد وتعطيل التسجيل العام واستعادة الوصول ومنع الحساب الثاني.
13. سلوك البحث بالاسم والهاتف والرقم اليدوي والفهارس اللازمة.
14. تخزين الوقت UTC وعرضه بالمنطقة المحلية وتعريف نافذة «خلال 30 يومًا».
15. سياسة حذف/أرشفة الدورات والتسجيلات؛ لا حذف فعلي تلقائي حاليًا.

## 10. بوابة السلامة والاعتماد

هذا المقترح ليس SQL أو migration ولا إذنًا بالتنفيذ. لا ينشئ قاعدة بيانات أو مشروع Supabase أو جداول أو سياسات أو أسرارًا أو استضافة أو كودًا ولا يغير بيانات. بعد المراجعة تُحسم القرارات المفتوحة، ثم تجرى مراجعة مستقلة للقيود وRLS واختبارات الاستعادة، ثم موافقة صريحة منفصلة قبل التنفيذ.

- **قرار معتمد — التسجيلات النشطة المتعارضة عند دمج طالبين:** إذا كان للطالبين تسجيل نشط في الدورة نفسها، يتوقف الدمج قبل أي كتابة حتى يحسم المستخدم التعارض صراحةً. لا يُلغى التسجيل المكرر ولا يُحذف أو يُدمج تلقائيًا أي سجل. بعد الحسم، لا يُنفذ الدمج إلا إذا بقيت جميع القيود والروابط والتواريخ سليمة؛ التنفيذ ذري بالكامل.

## 10. حسم القرارات النهائية وتوحيد المرجع قبل التنفيذ

هذه القرارات تحسم الغموض الوظيفي والتقني السابق في المقترح، لكنها لا تمنح إذنًا بإنشاء SQL أو migrations أو موارد.

### 10.1 التسجيلات عند دمج طالبين
- تُحفظ كل واقعة تسجيل تاريخية كسجل مستقل؛ لا تُدمج التسجيلات المكتملة أو المنسحبة أو الملغاة ولا تُحذف لمجرد تشابهها.
- إذا كان للطالبين تسجيلان نشطان في الدورة نفسها، يتوقف الدمج قبل أي كتابة. لا إلغاء تلقائي ولا حذف ولا اختيار تسجيل فائز.
- إذا لم يوجد تعارض نشط، يمكن إعادة ربط التسجيلات المستقلة بالطالب الأساسي المختار فقط بعد معاينة الروابط والتحقق من القيود. أي غموض في هوية سجل أو رابط يوقف الدمج.
- تبقى بيانات الطالب الأساسي كما هي افتراضيًا. تُعرض قيم الطالب الآخر المختلفة للمراجعة، ولا تُنسخ أو تُدمج تلقائيًا في الاسم أو الهاتف أو الرقم اليدوي أو الملاحظات. يبقى سجل الطالب المصدر محفوظًا تاريخيًا مع مرجع إلى الطالب الأساسي وتوقيت الدمج، ويُخفى من القوائم التشغيلية العادية.

### 10.2 حجوزات المعرفات التاريخية
- يحتفظ جدول الحجوزات بقيم المعرفات التاريخية مستقلة عن الصفوف التشغيلية، ولا يعتمد على مفاتيح أجنبية قابلة للكسر أو الحذف التتابعي. لا تكون هناك علاقة FK من سجل الحجز إلى صف الطالب أو الدورة التشغيلي؛ تحفظ هوية الكيان ونوع المعرف والقيمة وسبب الحجز نصيًا.
- يظل UUID المحجوز هوية تاريخية؛ لا يكفي تطابق UUID وحده للسماح بالاستعادة إذا تعارضت بيانات الهوية أو الروابط. التباس غير محسوم يوقف العملية قبل الكتابة.

### 10.3 التوليد الآمن للأرقام
- يُستخدم مولد PostgreSQL ذري مستقل لكل من أرقام الطلاب ورموز الدورات؛ يمنع استخدام MAX+1 أو توليد الأرقام في الواجهة.
- لا تُعاد المولدات إلى الخلف أبدًا. عند الاستعادة تُقفل مسارات التوليد والكتابة ذات الصلة، وتُقارن القيم الحالية والمستوردة والحجوزات، ثم يضبط المولد إلى موضع آمن لا يقل عن أعلى موضع سبق تخصيصه أو حجزه. لا يُعاد تخصيص رقم محجوز؛ وقد تُستهلك أرقام دون سجل عند الفشل وهذا مقبول.
- يجب إثبات سلامة التزامن باختبارات متزامنة في بيئة معزولة قبل اعتماد SQL. أي تعارض أو موضع غير قابل للإثبات يمنع الاستعادة.

### 10.4 حساب المالك الوحيد
- لا يُنشأ المالك تلقائيًا من أول حساب يسجل. يُهيأ معرف المالك عبر خطوة إعداد موثوقة خارج واجهة العميل، وتُرفض القراءة والكتابة إذا لم يكن المالك مضبوطًا أو تعذر التحقق منه.
- يُمنع التسجيل العام وإنشاء حساب ثانٍ، ولا تتضمن النسخة الاحتياطية بيانات المصادقة أو إعداد المالك. تغيير حساب المالك عملية إدارية منفصلة خارج نطاق النسخ والاستعادة.

### 10.5 الحقول والمدخلات
- الحدود القصوى: اسم الطالب 100 حرف، اسم الدورة 100، الهاتف 20، الرقم اليدوي 30، الملاحظات 1000 حرف. القيم الأطول تُرفض ولا تُقص.
- الأرقام التي يدخلها المستخدم أو يعرضها النظام تستخدم الأرقام الإنجليزية فقط. الهاتف يُخزن نصًا للحفاظ على + والصفر الأول.
- تطبيع الرقم اليدوي المعتمد: إزالة المسافات الطرفية فقط، ومقارنة الأحرف الإنجليزية دون حساسية لحالة الحرف، وإزالة الأصفار البادئة فقط إذا كانت القيمة كلها أرقامًا. المسافات الداخلية ذات معنى. تطبق القاعدة نفسها على التفرد والحجز والبحث والاستعادة.

### 10.6 صيغة النسخة وسلامتها
- يتضمن ZIP ملفات manifest وstudents وcourses وenrollments وidentifier_reservations؛ وجود كل ملف مطلوب إلزامي حتى عندما تكون المجموعة فارغة صراحةً.
- يتضمن manifest إصدار التنسيق والمخطط وقائمة الملفات وأحجامها وبصمات SHA-256. تتحقق المعاينة من البصمات والبنية والأنواع والعلاقات وحدود الحجم ومسارات ZIP قبل الكتابة.
- البصمات تكشف التلف أو الاختلاف عن manifest لكنها لا تثبت وحدها أن الحزمة لم تُعدّل عمدًا؛ لا يُدّعى وجود توقيع موثوق أو تشفير. تُعرض رسالة خصوصية لأن النسخة غير مشفرة.
- لا تُقبل ملفات أو تعليمات تنفيذية داخل الحزمة، ولا تُقبل الإصدارات غير المدعومة أو الملفات المطلوبة المفقودة.

### 10.7 التراجع وإعادة المحاولة
- كل استبدال أو دمج يُنفذ كوحدة ذرية واحدة مع إعادة فحص القيود داخل مسار التنفيذ، وليس اعتمادًا على المعاينة وحدها.
- بعد انقطاع الاتصال، لا يُعاد الطلب مباشرة. تُفحص الحالة الفعلية مقابل الخطة الأصلية؛ إن تعذر إثبات النتيجة، تتوقف العمليات الجديدة وتظهر حالة غير محسومة إلى حين التحقق.
- لا يُنشأ سجل عمليات دائم. يمكن عرض ملخص العملية الحالية فقط، ولا يُعلن النجاح إلا بعد تحقق ما بعد التنفيذ.


## 11. حفظ التسجيلات وأصلها عند الدمج

- لا يُحذف سجل الطالب المصدر عند الدمج. يحفظ `merged_into_student_id` و`merged_at`، ويُخفى عن القوائم التشغيلية العادية مع بقائه متاحًا في التاريخ.
- عند إعادة ربط تسجيل بالطالب الأساسي، يحفظ `original_student_id` هوية الطالب الذي أُنشئ له التسجيل أول مرة، بينما يشير `student_id` إلى الطالب الأساسي الحالي. لا يُعاد كتابة original_student_id مطلقًا.
- تبقى كل واقعة تسجيل سجلًا مستقلًا. وجود تسجيل نشط للطالبين في الدورة نفسها يوقف الدمج قبل الكتابة؛ لا إلغاء أو دمج تلقائي.
- النسخة الاحتياطية يجب أن تحفظ سجلات الطلاب المدموجين وعلامات الدمج وحقلي student_id وoriginal_student_id للتسجيلات.
