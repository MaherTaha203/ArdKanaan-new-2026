# بروتوكول النسخ الاحتياطي والاستعادة والاستبدال

**الحالة:** مواصفة تصميم قبل التنفيذ، وليست SQL أو migration أو إذنًا بإنشاء موارد أو تغيير بيانات.
**النطاق:** بيانات الطلاب والدورات والتسجيلات وحجوزات المعرفات والبيانات الوصفية المسموح بها. لا تشمل مصادقة Supabase أو كلمات المرور أو الجلسات أو الأسرار أو إعداد المالك.

## 1. القرار الأساسي

لا يجوز وصف الاستعادة أو الاستبدال بأنه «ذرّي بالكامل» إذا كان جزء من العمل يتم خارج معاملة PostgreSQL، مثل إنشاء ملف ZIP أو تخزين نسخة أمان. التصميم يفصل بين:
- **ذرية بيانات PostgreSQL:** كل تغييرات البيانات التشغيلية والحجوزات داخل معاملة واحدة، بحيث تنجح كلها أو تتراجع كلها.
- **حماية سير العمل الخارجي:** بوابة صيانة تمنع الكتابات الجديدة أثناء التقاط نسخة الأمان والاستبدال والتحقق. إذا وقع فشل خارج المعاملة، تبقى البوابة مغلقة افتراضيًا حتى تحقق موثوق أو تدخل إداري.
- **قابلية استرجاع الملف:** لا تكفي كتابة الملف؛ يجب التحقق من إمكانية قراءته واستخراج محتواه ومطابقة بياناته وبصماته قبل السماح بالاستبدال.

لا تُستخدم واجهة المتصفح وحدها لتنسيق هذا البروتوكول، ولا يُسمح للعميل بتجاوز بوابة الصيانة أو تعديلها مباشرة.

## 2. بوابة الصيانة والتنسيق

التصميم المقترح هو سجل تنسيق داخلي واحد في قاعدة البيانات، مثل `maintenance_gate`، لا يُتاح للعميل مباشرة. يحدد الحالة: `normal` أو `maintenance`، ومعرّف محاولة عشوائيًا مؤقتًا ووقت بدء العملية. هذا ليس سجل أحداث دائمًا ولا تقريرًا دائمًا؛ وظيفته منع الكتابات أثناء عملية حساسة.

### قواعد الكتابة

1. كل إجراء كتابة موثوق يبدأ بقفل صف البوابة `FOR UPDATE` داخل معاملته.
2. بعد القفل، يفحص أن الحالة `normal`. إن كانت `maintenance` يرفض العملية برسالة واضحة قبل أي كتابة.
3. يحتفظ الإجراء بقفل الصف حتى نهاية المعاملة. لذلك إذا بدأ كاتب قبل التحويل للصيانة، فإن بدء الصيانة ينتظر انتهاء معاملته؛ وإذا بدأت الصيانة أولًا، تُرفض الكتابات اللاحقة.
4. يجب أن يشمل ذلك جميع عمليات CRUD والتسجيل والدمج وتخصيص المعرفات وتصحيحها وفتح/إغلاق الدورات وأي إجراء آخر يغيّر بيانات مشمولة بالنسخة.
5. لا توجد صلاحية كتابة مباشرة من العميل تتجاوز إجراءات الكتابة والبوابة. تُراجع صلاحيات الجداول والدوال صراحة.
6. لا يعتمد التصميم على advisory lock عبر طلبات HTTP منفصلة؛ لا يجوز افتراض أن الطلبات المختلفة تشترك في جلسة PostgreSQL نفسها.
7. تفعيل الصيانة عملية إدارية موثوقة تقفل صف البوابة وتحوّل الحالة إلى `maintenance` بعد انتظار الكتابات السابقة. إلغاء الصيانة لا يتم تلقائيًا لمجرد انتهاء مهلة أو انقطاع عميل.

### الفشل الآمن

- لا توجد مهلة تنقلب بعدها البوابة إلى `normal` تلقائيًا؛ فقد تكون العملية لا تزال تنفذ أو تكون نتيجتها مجهولة.
- إذا فشلت العملية بعد تفعيل الصيانة، تبقى الصيانة مفعلة وتظهر رسالة أن النظام يحتاج إلى تحقق/استئناف إداري.
- لا يُفتح النظام إلا بعد فحص حالة البيانات والملف، والتأكد من عدم وجود معاملة استعادة جارية، ثم تنفيذ إجراء إداري موثوق.
- إذا تعذر إثبات الحالة الفعلية، تبقى الكتابات موقوفة. التوقف المؤقت أفضل من قبول كتابة قد تفسد استعادة غير محسومة.

## 3. إنشاء نسخة احتياطية

### المرحلة A — التحضير

1. تحقق من جلسة المالك ومن أن النظام ليس في وضع صيانة.
2. لا تُنشئ نسخة من مجموعة جداول تُقرأ في أوقات منفصلة؛ يجب أن تمثل البيانات لقطة متسقة واحدة.
3. حدّد إصدار تنسيق النسخة وإصدار المخطط وأسماء الملفات المطلوبة وحدود الأحجام قبل تنفيذ التصدير.

### المرحلة B — لقطة متسقة

1. تفعّل عملية التصدير بوابة الصيانة وفق البروتوكول، وتنتظر انتهاء الكتابات التي بدأت قبلها.
2. تُقرأ كل مجموعات البيانات المطلوبة من لقطة PostgreSQL متسقة واحدة: الطلاب، الدورات، التسجيلات، حجوزات المعرفات، والبيانات الوصفية المعتمدة.
3. يجب أن تحتوي اللقطة على السجلات التاريخية اللازمة، ومنها سجلات الطلاب المدموجين وحقول `merged_into_student_id` و`merged_at` و`original_student_id`.
4. لا تصدر بيانات Auth أو كلمات المرور أو رموز الجلسات أو الأسرار أو `system_config.owner_user_id`.
5. تُحوّل اللقطة إلى مخرجات ثابتة لا تتغير أثناء إنشاء الملف؛ لا تعتمد مرحلة ضغط ZIP على إعادة قراءة قاعدة البيانات بعد إلغاء الصيانة.
6. لا تُعاد البوابة إلى `normal` إلا بعد أن يؤكد المكوّن الموثوق أن اللقطة المتسقة أصبحت مخرجات ثابتة مكتملة، وسُلّمت إلى مسار موثوق أو خُزّنت في موقع مؤقت دائم قابل للقراءة. لا يكفي وجود البيانات في ذاكرة العميل أو نجاح استجابة HTTP وحده. بعد تأكيد التسليم الآمن، يمكن إعادة النظام إلى `normal` وبناء ZIP من اللقطة الثابتة دون إعادة قراءة قاعدة البيانات.
7. إذا انقطع الاتصال أو فشل التسليم أو تعذر إثبات تثبيت اللقطة خارج المعاملة، تبقى البوابة في `maintenance` حتى فحص موثوق واستئناف إداري؛ ولا تُعاد تلقائيًا بسبب انتهاء المهلة.

**بوابة تصميم:** يجب تحديد طريقة التقاط اللقطة المتسقة وتسليمها إلى مولد ZIP دون منح العميل صلاحيات إدارية. إذا جُمعت البيانات عبر عدة طلبات مستقلة، فلا تعتبر متسقة إلا إذا ثبت أنها تقرأ اللقطة نفسها أو بقيت الكتابات ممنوعة طوال الجمع. يجب تحديد مكان تثبيت اللقطة، وطريقة التحقق من اكتمالها، ومن يستطيع قراءتها، وكيفية إنهاء الاحتفاظ بها بعد التصدير.

### المرحلة C — بناء الحزمة والتحقق منها

الحزمة ZIP تحتوي على `manifest.json` وكل ملف بيانات مطلوب، بما في ذلك المجموعات الفارغة صراحةً. يتضمن manifest على الأقل:
- اسم التطبيق ومعرّف تنسيق النسخة وإصدار المخطط.
- وقت التصدير UTC.
- قائمة الملفات المطلوبة، والحجم بالبايت، وبصمة SHA-256 لكل ملف.
- قواعد ترميز النصوص والتواريخ وصيغ UUID.

يجب التحقق من الملف بعد إنشائه، لا قبل ضغطه فقط:
- يمكن فتح ZIP واستخراج جميع الملفات.
- لا ملفات مفقودة أو مكررة أو غير معروفة.
- لا مسارات مطلقة أو `..` أو مسارات استخراج غير آمنة.
- أحجام الملفات والحجم الكلي وعدد الملفات ضمن الحدود.
- كل بصمة وحجم يطابقان manifest.
- كل ملف صالح بنيويًا، وإصداره مدعوم، وأنواع الحقول والقيم والحالات صحيحة.
- كل UUID ومعرف فريد داخل الحزمة، وكل علاقة داخلية قابلة للتحقق.
- لا يحتوي manifest على أسرار أو بيانات مصادقة أو مالك.

**حد أمني:** SHA-256 يكتشف التلف العرضي أو عدم تطابق المحتوى مع manifest، لكنه لا يثبت المصدر إذا استطاع شخص تعديل الملف وmanifest معًا. لا تُدّعَ مقاومة العبث المتعمد دون توقيع موثوق بمفتاح محفوظ خارج الحزمة.

إذا فشل أي تحقق، لا تُعرض الحزمة على أنها نسخة سليمة. لا تُحذف نسخة سابقة صالحة لمجرد فشل التصدير الجديد.

## 4. معاينة الاستعادة قبل الكتابة

تُفحص الحزمة خارج مسار الكتابة التشغيلية، ولا تُنفذ أي كتابة للبيانات أثناء المعاينة.

1. فحص ZIP وmanifest والإصدار والملفات والأحجام والبصمات والمسارات.
2. فحص أنواع الحقول والحدود والحالات والتواريخ وتطبيع الأسماء والأرقام اليدوية.
3. فحص UUIDs والروابط وقيود التسجيلات، بما في ذلك `original_student_id` وحقول الدمج.
4. مقارنة حجوزات الحزمة بالحجوزات التاريخية الحالية عند التنفيذ؛ نتيجة المعاينة وحدها ليست نهائية لأن الحالة قد تتغير قبل التأكيد.
5. التحقق من أن مولدات أرقام الطلاب ورموز الدورات لن تُخفض وأن موضعها التالي آمن.
6. رفض الحزمة إذا غاب ملف مطلوب؛ الملف الغائب لا يعني مجموعة فارغة.
7. رفض UUID محجوز لا يمكن إثبات أنه الهوية الأصلية نفسها. UUID أو بصمة الملف وحدهما لا يكفيان لإثبات الهوية.
8. عرض الأعداد والتعارضات والأثر المتوقع وتحذير واضح إن كانت العملية استبدالًا كاملًا. لا يبدأ التنفيذ دون تأكيد مستقل بعد المعاينة.

## 5. استعادة أو استبدال كامل

### المرحلة A — الدخول إلى وضع الصيانة

1. بعد التأكيد، تبدأ العملية الإدارية الموثوقة بتفعيل بوابة الصيانة.
2. تنتظر انتهاء كل كتابات بدأت قبل تفعيل البوابة.
3. تعيد فحص صلاحية المالك والطلب والحزمة. لا تعتمد على معاينة سابقة وحدها.
4. تنشئ نسخة أمان حديثة من الحالة الحالية باستخدام بروتوكول النسخ نفسه.
5. تتحقق من قابلية قراءة نسخة الأمان واستخراجها ومطابقة محتواها. إذا فشل ذلك، لا تبدأ الاستبدال، وتبقى الصيانة مفعلة إلى أن تُحل الحالة بأمان.

### المرحلة B — فحص نهائي تحت الصيانة

بعد منع الكتابات، تُعاد مقارنة الحجوزات الحالية والواردة، وتُعاد جميع فحوص التعارضات والهوية والمولدات والعلاقات. أي تعارض غير محسوم يوقف التنفيذ قبل تغيير البيانات التشغيلية. لا يعاد ترقيم أي سجل ولا يُعاد ربط UUID بصمت.

### المرحلة C — معاملة PostgreSQL

ضمن معاملة واحدة:
1. تطبيق وضع الاستعادة المعلن داخل الإجراء الموثوق، دون تعطيل القيود بصمت.
2. استبدال نطاق البيانات التشغيلية المسموح فقط: الطلاب والدورات والتسجيلات، وفق السياسة المعتمدة.
3. دمج الحجوزات الواردة غير المتعارضة مع الاحتفاظ بكل الحجوزات الحالية. لا حذف لحجوزات تاريخية ولا تعديل روابطها لإجبار العملية على النجاح.
4. التحقق من روابط التسجيلات والدمج وسلامة المفاتيح الأجنبية والحالات والفهارس والتفرد.
5. ضبط مولدات أرقام الطلاب ورموز الدورات إلى الأمام فقط، بما لا يقل عن موضعها الآمن قبل الاستعادة وأعلى القيم المتوافقة المحجوزة أو المستوردة. إذا تعذر إثبات موضع آمن، تُرفض العملية.
6. إجراء فحوص نهائية على البيانات الفعلية قبل COMMIT.
7. أي فشل قبل COMMIT يؤدي إلى ROLLBACK كامل لتغييرات المعاملة. لا تُعلن نتيجة النجاح قبل تأكيد COMMIT والتحقق من الحالة.

### المرحلة D — بعد COMMIT

1. تُقرأ النتائج الفعلية وتُقارن بالأعداد والعلاقات والمولدات المتوقعة.
2. إذا نجح التحقق، تُعرض خلاصة العملية الحالية فقط؛ لا ينشأ سجل دائم للأحداث أو تقرير دائم.
3. لا تُعاد حالة البوابة إلى `normal` إلا بعد نجاح التحقق من البيانات المستعادة.
4. إذا فشل التحقق أو تعذر تحديد نتيجة COMMIT، تبقى البوابة في وضع الصيانة، ولا تعاد العملية تلقائيًا. يجب فحص الحالة الفعلية ونسخة الأمان ثم اتخاذ قرار استئناف إداري موثق.
5. لا تُحذف نسخة الأمان بسبب نجاح العملية مباشرة؛ يجب أن تبقى متاحة وفق سياسة الاحتفاظ المتفق عليها. مدة الاحتفاظ والتخزين الآمن قرار تشغيلي مستقل قبل الإطلاق.

## 6. انقطاع الاتصال والضغط المتكرر

- إذا انقطع الاتصال قبل تأكيد الطلب، لا تعاود الواجهة إرسال الاستعادة تلقائيًا.
- إذا انقطع بعد إرسال الطلب، لا تفترض النجاح أو الفشل. تفحص الحالة الفعلية من قناة موثوقة.
- إذا كانت البوابة `maintenance`، فهذا يعني منع الكتابات لا إثبات نجاح أو فشل الاستعادة.
- إذا لم يمكن معرفة ما إذا كانت المعاملة قد نفذت COMMIT، لا تبدأ استعادة ثانية ولا تفتح الكتابات؛ تحقق من الحالة التشغيلية الفعلية أولًا.
- لا يُفترض وجود سجل دائم لـ `request_id` أو نتائج العمليات. يمكن استعمال معرّف محاولة مؤقت لربط خطوات الإجراء الجاري، لكنه ليس بديلًا عن فحص قاعدة البيانات.
- لا توجد إعادة تلقائية بعد انتهاء المهلة أو إعادة تحميل الصفحة.

## 7. الاستبدال الكامل مقابل الدمج

- **الاستبدال الكامل** يبدل بيانات الطلاب والدورات والتسجيلات التشغيلية فقط. لا يبدل المصادقة أو إعداد المالك، ولا يمحو حجوزات المعرفات التاريخية الحالية.
- **الدمج** عملية مختلفة، لا تُستخدم تلقائيًا عند فشل الاستبدال. تحتاج اختيارًا صريحًا ومعاينة وحل التعارضات قبل الكتابة.
- لا يُحوّل الملف المفقود إلى مجموعة فارغة، ولا يُعتبر ZIP فارغًا طلبًا للاستبدال الفارغ إلا بعد تأكيد مستقل وصريح.
- لا يُفعّل التسجيل تلقائيًا إذا كان الطالب موقوفًا أو محذوفًا منطقيًا أو كانت الدورة مغلقة.
- لا تُحذف سجلات الطالب المصدر المدموج ولا حقول `original_student_id` التاريخية.

| الرمز | الاختبار | النتيجة المطلوبة |
|---|---|---|
| BAK-001 | إنشاء نسخة أثناء وجود كتابة قيد التنفيذ | تنتظر اللقطة انتهاء الكتابة أو تحصل على لقطة متسقة موثقة؛ لا بيانات نصف مكتوبة |
| BAK-002 | إنشاء ZIP ثم فتحه واستخراجه والتحقق منه | كل الملفات المطلوبة موجودة وسليمة ومتطابقة مع manifest |
| BAK-003 | ملف مفقود أو مكرر أو مسار غير آمن | رفض الحزمة قبل أي كتابة |
| BAK-004 | تغيير محتوى ملف دون تحديث البصمة | فشل التحقق |
| BAK-005 | تغيير ملف وmanifest وإعادة حساب SHA-256 | لا يُدّعى إثبات المصدر؛ تُطبق قواعد الهوية والتحذير |
| RST-001 | تعذر إنشاء نسخة أمان | لا يبدأ الاستبدال؛ تبقى الصيانة حتى التحقق |
| RST-002 | فشل بعد كل مرحلة من مراحل الاستبدال داخل المعاملة | تراجع كل تغييرات البيانات التشغيلية والحجوزات التي تمت ضمن المعاملة |
| RST-003 | فشل تحقق ما بعد COMMIT | تبقى الصيانة مفعلة؛ لا نجاح معلن ولا إعادة تلقائية |
| RST-004 | كاتب يبدأ قبل تفعيل الصيانة | لا يبدأ الاستبدال حتى ينتهي الكاتب |
| RST-005 | كاتب يصل بعد تفعيل الصيانة | يرفض قبل أي كتابة |
| RST-006 | تعارض UUID أو رقم محجوز | رفض قبل الكتابة؛ لا إعادة ربط أو ترقيم صامت |
| RST-007 | نسخة أقدم من موضع مولد المعرفات الحالي | لا تنخفض المولدات ولا يعاد استخدام رقم سابق |
| RST-008 | انقطاع الاتصال قبل/بعد COMMIT | لا إعادة تلقائية؛ فحص الحالة الفعلية مع بقاء الصيانة عند الغموض |
| RST-009 | محاولة عميل تعديل بوابة الصيانة أو تجاوزها | رفض من صلاحيات PostgreSQL/RLS |
| RST-010 | استعادة بعد دمج طلاب | حفظ سجلات المصدر وحقول الدمج و`original_student_id` والعلاقات |

يجب تنفيذ الاختبارات لاحقًا على PostgreSQL/Supabase معزول ببيانات اصطناعية، مع جلسات متزامنة فعلية وحقن فشل. هذه الوثيقة لا تثبت نجاح أي اختبار.

## 9. بوابات غير محسومة قبل SQL والإطلاق

1. اختيار تنفيذ موثوق لتفعيل بوابة الصيانة وتصدير لقطة متسقة وبناء ZIP دون إعطاء العميل امتيازات إدارية.
2. تحديد تخزين نسخة الأمان، صلاحيات الوصول إليها، التحقق من سلامتها، وسياسة الاحتفاظ بها.
3. تحديد الأدلة المقبولة لإثبات هوية UUID تاريخي؛ لا يُسمح بتجاوز التعارض عند عدم كفايتها.
4. تحديد كيفية عرض/استئناف حالة صيانة عالقة عبر إجراء إداري موثوق لا يفتح الكتابات تلقائيًا.
5. اعتماد حدود ZIP وعدد الملفات والأحجام والإصدارات وصيغ التواريخ.
6. تنفيذ اختبارات التزامن والفشل والتراجع فعليًا في بيئة معزولة قبل أي إطلاق.

## 10. حدود التنفيذ الحالية

لم تُكتب SQL أو migrations، ولم يُنشأ حساب أو مشروع Supabase، ولم تُشغّل اختبارات قاعدة بيانات فعلية. هذه مواصفة تصميمية فقط. لا تُعد موافقة على تنفيذها أو على إنشاء موارد، ولا تفتح PR ولا تدمج أي PR.
