# مخطط التنفيذ المقترح لقاعدة البيانات — بوابة ما قبل SQL

**الحالة:** تصميم للمراجعة فقط؛ ليس SQL أو migration، ولا إذنًا بإنشاء موارد أو تنفيذ تغييرات.
**الفرع:** `docs/final-security-consistency-review`.

## 1. قرار التنفيذ المحافظ

لأن الإصدار الأول مخصص لحساب بشري واحد، نعتمد بروتوكول تنسيق مرجعيًا واحدًا: كل إجراء يغيّر بيانات التشغيل أو حجوزات المعرفات أو مولداتها يبدأ بقفل صف `maintenance_gate` باستخدام `SELECT ... FOR UPDATE` داخل معاملة PostgreSQL، ثم يتحقق من أن الحالة `normal` ومن المالك والقيود، ويحتفظ بالقفل حتى نهاية المعاملة. إذا كانت الحالة `maintenance` يرفض الإجراء قبل أي كتابة. يشمل ذلك CRUD، الترقيم، تصحيح الأرقام، فتح/إغلاق الدورات، التسجيل، الدمج وأي مسار آخر يغيّر بيانات مشمولة بالنسخ.

بوابة الصف هي المرجع الوحيد لتنسيق الكتابات الاعتيادية مع النسخ والاستعادة والاستبدال. عملية إدارية موثوقة تغيّر حالة البوابة إلى `maintenance` بعد انتظار الكتابات السابقة، وتبقى الكتابات الجديدة مرفوضة حتى إعادة فتحها إداريًا بعد التحقق. لا يُعتمد على advisory lock باعتباره بديلًا لهذه البوابة، ولا يُفترض أن طلبات HTTP المختلفة تشترك في جلسة PostgreSQL نفسها. يجوز استخدام advisory lock إضافي داخل معاملة واحدة فقط إذا وُثّق سبب الحاجة إليه؛ ولا يغيّر ذلك بروتوكول البوابة.

بعد قفل البوابة تعيد الإجراءات قراءة الحالة والتحقق من المالك والقيود؛ لا تعتمد على معاينة قديمة. وتبقى قيود وفهارس PostgreSQL إلزامية كخط دفاع إضافي. لا يحصل العميل على صلاحيات كتابة مباشرة للجداول أو البوابة، لأن أي مسار يتجاوز الإجراءات الموثوقة يمكنه تجاوز البروتوكول. هذا الاختيار يقلل توازي الكتابات عمدًا؛ لا يُستبدل بقفل أدق قبل اختبار مستقل.

## 2. خريطة الجداول والقيود

| الجدول | القيود المطلوبة |
|---|---|
| `students` | PK على `id`؛ UNIQUE على `student_number`؛ حالة محددة؛ الاسم غير فارغ؛ حدود الحقول؛ تفرد الرقم اليدوي الحالي بعد التطبيع؛ فهارس البحث |
| `courses` | PK؛ UNIQUE على `course_code`؛ حالة محددة؛ نهاية لا تسبق البداية؛ فهرس فريد جزئي للاسم المعياري للدورات المفتوحة |
| `enrollments` | PK؛ FK للطالب والدورة و`original_student_id` دون حذف تتابعي؛ حالة محددة؛ فهرس فريد جزئي لـ(`student_id`, `course_id`) حيث الحالة active |
| `identifier_reservations` | PK؛ UNIQUE على (`identifier_kind`, `normalized_value`)؛ نوع حجز محدد؛ قيم تاريخية مستقلة عن الصفوف التشغيلية، بلا FK أو CASCADE يحذف الحجز |
| `system_config` | صف singleton واحد؛ مالك غير فارغ؛ منع الكتابة المباشرة من العميل |

يجب أن تستخدم جميع المسارات دوال تطبيع موحدة. اسم الطالب/الدورة: إزالة المسافات الطرفية ودمج المسافات المتكررة فقط. الرقم اليدوي: إزالة المسافات الطرفية، وتوحيد حالة الأحرف الإنجليزية، وتجاهل الأصفار الأولى إذا كانت القيمة أرقامًا فقط؛ تبقى المسافات الداخلية ذات معنى. يجب أن تطابق خوارزمية التطبيع قواعد الفهارس والبحث والحجز والاستعادة.

## 3. إجراءات الكتابة الموثوقة

| العملية | التنفيذ الذري المطلوب | حالات الرفض |
|---|---|---|
| إنشاء طالب أو دورة | أخذ القفل، التحقق من المالك، توليد UUID والمعرف المقروء، حجزهما، إنشاء السجل، التحقق من التطابق | أي تصادم حجز أو فشل |
| تصحيح الرقم اليدوي | تطبيع الرقم الجديد، حجزه، إبقاء القديم محجوزًا، تسجيل سبب التصحيح وتحديث الطالب | قيمة محجوزة أو فارغة |
| فتح دورة | إعادة فحص الاسم المعياري وحالة الدورات تحت القفل؛ مع فهرس فريد جزئي نهائي | اسم مفتوح مكرر أو تاريخ غير صالح |
| إنشاء تسجيل | أخذ القفل، إعادة فحص أن الطالب نشط وغير محذوف والدورة مفتوحة، ثم الإدخال | طالب موقوف/محذوف، دورة مغلقة، أو تسجيل نشط مكرر |
| تغيير حالة تسجيل | السماح بالانتقال من active إلى حالة نهائية فقط | إعادة تنشيط تسجيل نهائي أو تغيير `original_student_id` |
| دمج طالبين | قفل موحد، إعادة فحص أهلية الطرفين وسلاسل الدمج والتعارضات، ثم نقل العلاقات المسموح بها مع إبقاء المصدر والحجوزات | طرف ضمن تاريخ دمج سابق، تسجيل نشط في الدورة نفسها، أو تعارض غير محسوم |
| إنشاء نسخة | لقطة متسقة للبيانات التشغيلية والحجوزات، مع manifest وبصمات | ملفات ناقصة أو لقطة غير متسقة |
| استعادة/استبدال | معاينة أولية، تأكيد منفصل، القفل نفسه، إعادة الفحص، نسخة أمان، تغييرات تشغيلية وحجوزات ومولدات، تحقق نهائي ثم COMMIT | أي تعارض غير محسوم أو فشل في النسخة/التحقق |

كل عملية متعددة الخطوات يجب أن تكون كلها أو لا شيء داخل معاملة PostgreSQL واحدة حيثما أمكن. إذا كان إنشاء ZIP أو نسخة الأمان يعتمد على تخزين خارجي، فلا توصف العملية كاملة بأنها ذرية تلقائيًا؛ يجب تصميم المراحل الخارجية والتعامل مع فشل كل مرحلة قبل كتابة SQL.

## 4. قواعد التزامن والاستعادة

- الفهرس الفريد الجزئي يمنع التسجيل النشط المكرر، لكنه لا يثبت حالة الطالب أو الدورة. هذه الحالات تفحص داخل إجراء الكتابة بعد أخذ القفل مباشرة.
- فهرس الاسم المعياري الفريد الجزئي يمنع سباق فتح دورتين بالاسم نفسه.
- إيقاف الطالب وإغلاق الدورة يستخدمان القفل نفسه. لا تتغير التسجيلات النشطة القائمة تلقائيًا.
- إنشاء الطالب/الدورة يحجز UUID والمعرف المقروء ضمن المعاملة نفسها. فجوات التسلسل بعد الفشل مقبولة؛ إعادة الاستخدام ممنوعة.
- حجوزات المعرفات مستقلة عن الصفوف التشغيلية ولا تمحى عند الاستبدال. لا تستخدم UPSERT لتغيير روابط حجز تاريخي بغرض إجبار الاستعادة على النجاح.
- الاستعادة تقارن نوع المعرف والقيمة المعيارية والهوية التاريخية وروابطها. عند عدم كفاية الأدلة تتوقف قبل الكتابة.
- UUID أو SHA-256 داخل ZIP لا يثبت وحده مصدر الحزمة أو عدم العبث المتعمد. إذا لم تتوفر أدلة موثوقة تكفي لإثبات الهوية الأصلية، يجب رفض الحالة الملتبسة بدل الادعاء بأن الهوية مثبتة.
- لا تُخفض مولدات أرقام الطلاب أو رموز الدورات. تضبط للأمام فقط وفق موضع المولد الحالي وأعلى الحجوزات/القيم المتوافقة؛ إذا تعذر إثبات موضع آمن، تتوقف الاستعادة.
- لا تكتب الاستعادة اعتمادًا على المعاينة وحدها: بعد القفل تعاد كل فحوص الهوية والتعارضات. يجب أن تتراجع المعاملة كاملة عند أي فشل قبل COMMIT.
- إذا انقطع الاتصال بعد إرسال طلب حساس، لا يُعاد تلقائيًا. تُفحص الحالة الفعلية، وعند الغموض توقف العمليات الحساسة الجديدة حتى التحقق؛ لا نفترض وجود سجل نتائج دائم.

## 5. أمن PostgreSQL وSupabase

- تفعيل RLS على الجداول المكشوفة، مع ضبط GRANT/REVOKE صراحة. لا وصول لـ anon ولا تسجيل عام.
- لا كتابة مباشرة من العميل إلى جداول التشغيل أو الحجوزات أو إعداد المالك؛ كل كتابة عبر إجراء موثوق محدود.
- كل إجراء حساس يتحقق من جلسة صالحة ومن مطابقة `auth.uid()` مع `owner_user_id` المهيأ إداريًا. غياب المالك أو عدم تطابقه يعني الرفض.
- أي دالة `SECURITY DEFINER` لها `search_path` ثابت وآمن، ومراجع مؤهلة بالمخطط، وصلاحية EXECUTE محدودة. لا يوضع مفتاح service_role في العميل.
- تهيئة المالك إجراء إداري منفصل خارج العميل بعد تعطيل التسجيل العام؛ لا يصبح أول مستخدم المالك تلقائيًا.
- لا تُستخدم جلسة superuser لإثبات فعالية RLS؛ تختبر المسارات بدور anon وauthenticated غير المالك والمالك.

## 6. اختبارات إلزامية قبل اعتماد SQL

1. قيود الحقول والحالات والتواريخ والأسماء المعيارية.
2. توليد وحجز متزامن للمعرفات، وإعادة استخدام الرقم اليدوي القديم، وفشل بعد الحجز.
3. تسجيل طالب موقوف أو دورة مغلقة، وطلبان متزامنان للتسجيل نفسه، وإعادة تنشيط تسجيل نهائي.
4. جلستان تفتحان دورة بالاسم المعياري نفسه.
5. الدمج مع تعارض تسجيل نشط، وسلاسل دمج، وحقن فشل بعد كل مرحلة.
6. استعادة بملف ناقص/تالف، وUUID ملتبس، وحجز متعارض، ومولد أقدم، وحقن فشل في كل مرحلة.
7. محاولة الكتابة المباشرة بدوري anon وauthenticated، واستدعاء إجراء دون صلاحية، وتغيير إعداد المالك.
8. قطع الاتصال قبل COMMIT وبعده، والتحقق من الحالة دون إعادة تلقائية.
9. نسخة متسقة أثناء الكتابات ثم استعادتها في بيئة معزولة ومقارنة العلاقات والحجوزات والمولدات.

يجب تشغيل الاختبارات لاحقًا على PostgreSQL/Supabase معزول ببيانات اصطناعية وجلسات متعددة فعلية. لا تُعد أسماء الاختبارات أو هذه الوثيقة دليل نجاح.

## 7. المسائل التي لا تزال بوابة قبل SQL

1. تحديد آلية نسخة الأمان القابلة للتحقق وكيفية إدارتها إذا كانت خارج معاملة PostgreSQL.
2. تحديد الحد الأدنى من الأدلة الموثوقة التي تسمح باستعادة UUID تاريخي؛ الحالات غير المثبتة تُرفض.
3. إثبات أن جميع الكتابات تمر عبر الإجراءات الملتزمة بالقفل ولا توجد صلاحيات مباشرة تتجاوزها.
4. تحديد آلية لقطة نسخة متسقة تشمل الحجوزات والبيانات الوصفية دون Auth أو الأسرار.
5. توثيق سلوك انقطاع الاتصال عندما لا يوجد سجل نتائج دائم.
6. إثبات أن دوال التطبيع صالحة للفهرسة ومتطابقة في كل المسارات.

## 8. حدود الحالة

لم تُكتب SQL أو migrations، ولم يُنشأ حساب أو مشروع Supabase، ولم تُشغّل اختبارات قاعدة بيانات فعلية. هذه وثيقة تصميم فقط، ولا تثبت أمان التنفيذ أو جاهزيته. لا يُفتح PR جديد ولا يُدمج أي PR ضمن هذه الخطوة.
